# Exploration: add-technical-grounding-safety-gates

## Current State

The merged deterministic grounded-query kernel (`build-production-core-query-path`, `e6234d1`) and the just-merged quality evaluation harness (`add-opsknowledge-quality-evaluation-harness`, `d0caa7e`) together produce a reproducible, development-only Phase 2 baseline, but they do not yet enforce the **release-blocking safety thresholds** that `RAG_ROADMAP.md` Phase 2 promises as one of its "Expected outputs" (line 199) and that the phase acceptance direction requires ("no unsupported technical claim may pass the evaluation gate", line 197).

The merged `add-opsknowledge-quality-evaluation-harness` change explicitly defers thresholds to this change. Both its spec and proposal lock the boundary: "It MUST emit numbers only and define no release thresholds" (spec requirement 5, `quality-evaluation-harness/spec.md` line 51) and "Numbers only; `add-technical-grounding-safety-gates` owns thresholds" (`proposal.md` line 29). The `evaluation-dataset/spec.md` likewise forbids the dataset or validator from owning metrics, baselines, or release thresholds (line 349). The boundary is clean and the current contract deliberately leaves the threshold surface empty.

What is already in place and is the substrate of this change:

- **Kernel safety logic (consumed unchanged).** `backend/features/query/application.py` is the in-process six-state outcome engine. `_screen(...)` blocks `sensitive_blocked`, `prompt_override_blocked`, and `out_of_scope`; `_route_language(...)` enforces bilingual isolation; `_has_contradictory_revisions(...)` detects inter-revision contradiction; `_valid_citations(...)` enforces the citation allow-list; `_provider_failure_response(...)` maps typed `ProviderFailure` to `unavailable` with the right reason code. The kernel already produces every reason code the gates need to assert.
- **Harness reporting (consumed unchanged).** `backend/features/evaluation/application.py` runs the 34-case evaluation (32 base scenarios + 2 injected provider-failure cases), and `backend/features/evaluation/domain.py::compute_metrics(...)` returns five `MetricSignal` values with explicit denominators: `outcome_classification` (34/34), `citation_exact_match` (34/34), `language_routing` (34/34), `sensitive_block` (2/2 sensitive cases), `contradiction_detection` (4/4 contradictory cases).
- **Safe serialization (consumed unchanged).** `backend/features/evaluation/adapters/report.py` emits an allowlisted JSON summary, JSONL records, and human output with no question/answer/citation content. `ReportAdapter.promote(...)` is the atomic "current/previous" baseline store.
- **Opt-in wiring (consumed unchanged).** `Makefile` `eval-quality` runs `python -m backend.features.evaluation.cli evaluation-dataset`. `make ci` does not run the harness and the canonical gate is unchanged. The dataset is validated upstream via `check-evaluation-dataset`.
- **Reviewed baseline (already committed).** `evaluation-runs/current/summary.json` shows the present state after the quality-harness Unit 3 merge: `outcome_classification 9/34`, `citation_exact_match 10/34`, `language_routing 34/34`, `sensitive_block 2/2`, `contradiction_detection 0/4`. The dataset of 32 base scenarios includes four contradictory cases and two sensitive cases; the current numbers mean the kernel is still failing to detect contradiction in the four contradiction scenarios, which is exactly the kind of regression the safety gate is supposed to catch before the harness is widened to language/abstention evaluation.
- **Authority order.** `AGENTS.md` > `RAG_ROADMAP.md` > `docs/architecture/platform-architecture.md` > SDD artifacts. Cross-phase safety invariants apply unchanged. `make ci` is the canonical local gate and is **not** to be widened without an explicit decision; `RDD` and `4R` remain disabled under upstream issue #1892. The development-only synthetic corpus exception and the public-OpenAI free-text demo risk remain two separate concerns.

What is **not** in place and is what this change must add:

- Numeric pass/fail thresholds per safety signal with a stable reason-code vocabulary.
- A fail-closed gate that compares the run's `MetricSignal`s against the thresholds and either approves, blocks, or escalates.
- Per-scenario claim-evidence checks (the harness currently counts `citations_match` at the case level; the gates must additionally enforce that any `supported` case carries a non-empty, allow-listed citation set and that no `insufficient_information` case yields citations — the whole-answer blocking rule from the kernel, lifted to a release contract).
- A gate-runner command (`make eval-quality-gate` or equivalent) that runs the same harness, compares against thresholds, exits non-zero on regression, and writes a reviewed safe gate report.
- A gate spec delta on a new `technical-grounding-safety-gates` capability, with an explicit `Makefile` ordering test that the new gate target does not enter `make ci` for this change.
- A reviewed, committed "first approved gate baseline" under `evaluation-runs/` that records both the numbers and the threshold decisions for the next change to compare against.

The change is bounded by the Phase 2 scope: thresholds only, no new metrics, no new dataset cases, no kernel or corpus mutation, no live provider, no persistence beyond the `evaluation-runs/` baseline, no new dependency, no `make ci` widening in this slice.

Likely new files: `backend/features/evaluation/gates/policy.py` (threshold table + reason codes), `backend/features/evaluation/gates/runner.py` (compare + decide), `backend/features/evaluation/gates/report.py` (safe gate-report serializer).
- `backend/features/evaluation/adapters/report.py` — **consumed unchanged for the existing JSON/JSONL/human output.** The gate report is a new, allowlisted serializer that adds gate decision fields (pass/block/escalate, threshold values, deltas vs. previous baseline) but never adds content fields. A focused test must assert the allowlist.
- `backend/features/evaluation/cli.py` — **extended, not replaced.** A new subcommand (e.g. `python -m backend.features.evaluation.cli gate` or a new entry point) drives the gate runner. The existing opt-in `make eval-quality` continues to emit the numbers-only baseline and must not block or pass/fail; the new subcommand is the release gate.

Use `pytest.mark.parametrize` with literal/direct-Name containers per the existing convention. The harness's `FrozenClock` and the gate's `FrozenClock` must be independent injections.
- `evaluation-runs/` — **new `gate/` baseline directory** holding the first approved gate decision (parallel to the existing `current/summary.json` and `current/report.txt`). This is a minimal, in-place edit, not a new requirement, and it keeps the spec internally consistent with the new gate. (A second candidate approach is to leave the harness spec untouched and add a new `technical-grounding-safety-gates` capability with no MODIFIED blocks; that is the recommended approach because the kernel change is still unarchived and a MODIFIED here would force a sequencing dependency on the issue #1892 archive.)
- `openspec/specs/technical-grounding-safety-gates/spec.md` — **new** if the recommended approach is taken. Owns the threshold contract, the per-scenario whole-answer blocking rules, the gate report schema, and the "no `make ci` widening in this slice" boundary.
- `RAG_ROADMAP.md` — **no edit in this exploration.** The Phase 2 checkbox for `add-technical-grounding-safety-gates` may move from `[ ]` to `[x]` only on archived verification, not on this exploration or on proposal acceptance.
- `AGENTS.md`, `docs/architecture/platform-architecture.md`, `RAG_ROADMAP.md` cross-phase safety invariants — **no edit.** The whole-answer blocking, evidence-only claims, replaceable providers, safe-field logging, no excluded dependencies, and no `make ci` widening are preserved unchanged.

## Approaches

1. **In-process gate runner with a separate opt-in `make eval-quality-gate` target (recommended).** Add `backend/features/evaluation/gates/{policy,runner,report}.py`. The policy module holds a frozen, reviewed threshold table per `MetricSignal` plus a per-scenario whole-answer rule set (no `supported` case may have an empty citation set; no `insufficient_information` case may yield any citation; no `contradictory_information` case may have a citation set larger than the two contradictory fragments; no `unavailable` with `sensitive_blocked` may have a citation set; no `unavailable` with `provider-timeout`/`provider-rate-limit`/`provider-outage` may have a citation set). The runner loads the unchanged harness summary, compares each `MetricSignal` to its threshold, evaluates the per-scenario rules, and produces a gate decision: `pass`, `block` (release-blocking regression on at least one threshold), or `escalate` (any cross-phase safety invariant like sensitive-block is below 100%). The gate report is a new allowlisted serializer that records per-signal `{threshold, observed, decision, reason_code}` and a final `gate_decision` plus a delta vs. the previous reviewed gate baseline. The CLI gains a new subcommand (`gate`); `make eval-quality-gate` runs the same frozen clock, depends on `eval-quality`, and exits non-zero on `block`. `make ci` is unchanged. The new `technical-grounding-safety-gates` capability owns the contract; the `quality-evaluation-harness` capability is not modified. One reviewed "first approved gate baseline" is committed under `evaluation-runs/gate/`. Five focused tests cover policy, runner, report, Makefile ordering, and a frozen-clock regression case. The change stays inside the development profile, never logs content, never persists question/answer/citation/provider-payload bytes, reuses the existing `emit_safe_log` discipline, introduces no new dependency, no live provider, no embeddings, no HTTP, no PostgreSQL, no reranking, and no `make ci` widening. The orchestrator is expected to receive an authored-line forecast near the 400-line review budget: policy table (~40 lines), runner (~80 lines), gate report serializer (~70 lines), CLI subcommand wiring (~20 lines), Makefile target (~5 lines), focused tests (~150 lines), gate baseline artifacts (~20 lines).
   - Pros: stays inside the existing dev profile and the kernel/harness invariants; reuses the five `MetricSignal`s and the `ReportAdapter`; never re-implements the harness; the per-scenario rules lift the kernel's whole-answer blocking to a release contract; the gate target is opt-in and explicitly does not enter `make ci`; no dependency surface; the "previous/current" baseline discipline gives Phase 2 the comparison backbone the roadmap expects.
   - Cons: a second CLI subcommand doubles the developer loop surface; the threshold table becomes a reviewed artifact that must be updated when the kernel improves (e.g. when `contradiction_detection` finally reaches 4/4 the table may need to be tightened); the per-scenario whole-answer rules may overlap with kernel invariants and need careful wording to avoid drift.
   - Effort: Medium.

2. **Threshold policy embedded in the existing harness with a `--gate` flag and a single CLI.** Add the threshold table and the per-scenario rules to `backend/features/evaluation/application.py`, add a `--gate` argument to `cli.py`, and have `make eval-quality` print a "PASS" or "BLOCK" line on top of the existing human output. The single CLI stays, the human output gains a one-line decision, and the JSON summary gains a `gate_decision` field.
   - Pros: smallest visible surface; one command to remember; no new Makefile target; the existing focused tests cover most of the runner; one round of developer-loop changes instead of two.
   - Cons: the spec for `quality-evaluation-harness` currently says "MUST emit numbers only and define no release thresholds" — adding thresholds to the same artifact requires a MODIFIED requirement against the same capability, which the merged harness change already locks at the open-kernel-archive sequencing dependency; the per-scenario whole-answer rules risk being read as a quiet expansion of the harness scope; the gate decision and the harness numbers are conflated in one report, which the merged spec explicitly separated; the "previous baseline" comparison loses meaning when the previous baseline is numbers-only and the new one is numbers-plus-decision.
   - Effort: Low.

3. **Phase 2 evaluation runner with embeddings, live provider, and persistence to PostgreSQL.** Build the full Phase 2 metric set (Recall@K, semantic contradiction labeling, p95 latency, cost per query), wire a live OpenAI provider, persist run history to PostgreSQL, and emit release-blocking thresholds as part of a wider Phase 2 release gate.
   - Pros: strongest quality gates before further slices; would catch regressions in live-provider behavior.
   - Cons: introduces a live provider, embeddings, persistence, and a dependency surface; collides with the prototype/corporate boundary; collides with the excluded-dependency list; the merged kernel is explicitly Phase 1 foundational and the harness is explicitly Phase 2 measurement; live provider and embeddings belong to Phases 3+; the per-scenario claim-evidence contract can be enforced without a live provider because the kernel is deterministic. Rejected for this slice.

## Recommendation

Use **Approach 1**. The change should enter proposal with the narrow scope of **a deterministic, in-process, dependency-free, development-profile-only technical-grounding safety gate** that:

1. Re-uses the unchanged harness runner (`run_evaluation`) and the unchanged `compute_metrics` to obtain the five `MetricSignal`s; it does not invoke the kernel, the retriever, the provider, or the corpus loader directly.
2. Holds a reviewed, frozen threshold table per `MetricSignal` in a new `gates/policy.py`. The table records `metric_name`, `threshold_value`, `decision_class` (`pass`/`block`/`escalate`), and a stable `reason_code`. The table is the single source of truth for the gate and is reviewed as part of the change.
3. Evaluates a small, reviewed per-scenario whole-answer rule set: no `supported` case may have an empty citation set; no `insufficient_information` case may have any citation; no `contradictory_information` case may have more than the two contradictory fragment IDs; no `unavailable`/`sensitive_blocked` may have any citation; no `unavailable`/`provider-*` may have any citation; every `sensitive` case must be blocked; every `contradictory` case must be detected; every `injected-provider-failure-*` case must end `unavailable` with the typed `provider-timeout` reason.
4. Compares the run against the previous reviewed gate baseline (`evaluation-runs/gate/previous/`) and records a per-signal `delta` and `direction` (`improved`/`regressed`/`unchanged`).
5. Produces a gate decision: `pass` (all thresholds met, all per-scenario rules satisfied, no regression vs. previous), `block` (at least one threshold or per-scenario rule failed), or `escalate` (any cross-phase safety invariant is below 100%, e.g. `sensitive_block < 1.0`). The gate runner never modifies the harness numbers; the numbers stay allowlisted and threshold-free on the harness path.
6. Emits a new allowlisted gate report under `evaluation-runs/gate/current/` (atomic `current/previous` promotion via the unchanged `ReportAdapter.promote(...)`). The gate report contains only IDs, enums, version, threshold values, observed values, deltas, decision, and reason codes; it never contains question, answer, citation content, claim text, or provider payloads.
7. Adds a new `make eval-quality-gate` target that depends on `eval-quality`, runs the gate runner, and exits non-zero on `block`. The target is opt-in; `make ci` and `ci-pr2a` are unchanged. A new `tests/architecture/test_safety_gates_makefile_order.py` enforces the ordering.
8. Adds a new `python -m backend.features.evaluation.cli gate` subcommand so the gate can be driven from CI later (this slice keeps the gate out of `make ci` but exposes the subcommand for future wiring under a separate change).
9. Stays inside the development profile; never logs content; never persists question, answer, citation, claim, or provider payload; reuses the existing `emit_safe_log` / `SAFE_LOG_FIELDS` discipline and the `Clock` protocol; introduces no new production dependency, no live provider, no HTTP, no PostgreSQL, no embeddings, no reranking, and no `make ci` widening.

The proposal should explicitly **exclude** the additional Phase 2 metrics (Recall@K, p95 latency, cost per query, semantic contradiction labeling, language-routing accuracy, abstention-accuracy, unsupported-claim escape rate, query latency, hybrid retrieval, reranking, or OCR quality), dataset changes, kernel or corpus changes, embeddings, live OpenAI/Azure adapters, vector stores, persistence beyond `evaluation-runs/gate/`, HTTP, sessions, authentication, web UI, and corporate data. The added Phase 2 metrics and OCR quality belong to `add-language-and-abstention-evaluation` and the later Phase 3+ slices; embeddings and live providers remain Phase 3+ / Phase 8.

The orchestrator should expect an authored-line forecast near the 400-line review budget, with the policy, runner, gate report, CLI subcommand wiring, focused tests, and one reviewed gate baseline each contributing. The forecast should be split by work unit in the tasks phase so the ask-on-risk decision can be made before any code lands.

## Risks

- **Outstanding kernel archive blocks a MODIFIED on `quality-evaluation-harness`.** A delta against the merged harness capability cannot be merged into `openspec/specs/quality-evaluation-harness/spec.md` until `build-production-core-query-path` is archived. The proposal will avoid this by adding the gates as a new `technical-grounding-safety-gates` capability with no MODIFIED block. This is a sequencing decision the maintainer must confirm.
- **Threshold table is a reviewed artifact.** The threshold values must be set with care: too tight and the gate will block legitimate iterations; too loose and the gate will not protect the cross-phase safety invariants. The current baseline (`outcome_classification 9/34`, `contradiction_detection 0/4`) shows that the kernel still has work to do before contradiction detection is reliable; the gate must not be set so high that it blocks legitimate kernel improvements. The proposal will ask the maintainer to set the first threshold values explicitly.
- **Whole-answer blocking rule may overlap with the kernel.** The kernel already enforces citation allow-listing and contradiction detection. The gate's per-scenario rules must be worded as a release contract over the kernel's output, not as a re-implementation. The proposal will treat the per-scenario rules as a **read-only** assertion that the kernel's invariants hold, and any rule that fails will be raised as a `block` with a stable reason code that the kernel team can act on.
- **400-line review budget is the binding constraint.** The merged kernel, the harness Unit 3 candidate, and the prior explore notes all show that this repo's bounded slices regularly exceed 400 native lines. The gate change must forecast the budget per work unit and ask before splitting into chained PRs. The recommended forecast is one chain of two chained PRs (threshold policy + runner + first approved baseline in the first PR, gate report + Makefile + CLI subcommand + focused tests in the second).
- **Prototype/corporate boundary must not blur.** The gate runs only under the development profile and the existing fail-closed synthetic boundary. A future change that wires the gate into a live OpenAI/Azure provider, or that reuses it against corporate data, would violate the boundary and require a separate SDD change.
- **Excluded dependencies and reranking.** The gate change must not introduce any reranking, embeddings, or vector-store dependency; it must use the merged harness's numeric signals unchanged.
- **No content in logs or reports.** Threshold values, observed values, deltas, decision, reason codes, run id, contract version, profile, and duration are safe. Question text, answer text, citation content, claim text, scenario `claim_expectation` text, and provider payload text are not. The gate report schema must be reviewed against `SAFE_LOG_FIELDS` and the `SafeResponse` content-free surface before merge.
- **Clock and determinism.** The gate must inject a `Clock` and a frozen `FrozenClock` in tests; using `time.monotonic()` directly would break determinism and the `make eval-quality-gate` reproducibility contract. The gate may share the harness's `FrozenClock` timestamp or carry its own, but the report must record which one was used.
- **Makefile ordering.** Adding a new `make eval-quality-gate` target must not perturb the existing `make ci` or `ci-pr2a` order. The new target is opt-in; the new `tests/architecture/test_safety_gates_makefile_order.py` must prove the absence of widening.
- **`make ci` widening is a separate decision.** Wiring `make eval-quality-gate` into `make ci` is out of scope for this change. The next change (`add-language-and-abstention-evaluation`) may revisit this if the maintainer wants CI to fail on a gate regression; that decision is not made here.
- **Roadmap completion discipline.** The Phase 2 candidate checkbox for `add-technical-grounding-safety-gates` remains unchecked until archived; this exploration and the proposal do not complete the phase. The maintainer must not be told otherwise.
- **RDD and 4R remain disabled.** Per the session preflight, `RDD` and review work remain disabled until upstream Gentle AI issue #1892 is fixed. The change is therefore deliverable and verifiable, but a formal `RDD` review receipt cannot be claimed.
- **Excluded dependency reconciliation.** Adding any new direct production dependency to `pyproject.toml` or `uv.lock` would fail the canonical `make ci` gate. The gate change must add zero new dependencies.

## Ready for Proposal

**Conditional Yes.** The repository evidence is sufficient for a proposal **provided the orchestrator confirms four sequencing decisions before the proposal phase runs**:

1. The proposal will create a new `technical-grounding-safety-gates` capability and will **not** add a `MODIFIED` requirement against `quality-evaluation-harness`. The merged harness spec's "numbers only, no thresholds" rule stays as is; thresholds live in the new capability.
2. The first reviewed threshold table is set in the proposal by the maintainer, with explicit `decision_class` and `reason_code` per signal. The current harness baseline (`outcome_classification 9/34`, `contradiction_detection 0/4`) shows the threshold values must be conservative in this first slice; tightening them is a follow-up change after the kernel/harness mature.
3. The per-scenario whole-answer rules are a release contract over the kernel's invariants, not a re-implementation. A rule failure is a `block` with a stable reason code that the kernel team can act on.
4. The change ships one reviewed "first approved gate baseline" under `evaluation-runs/gate/` and keeps `make ci` and `ci-pr2a` ordering and membership unchanged.

No code, no existing artifact, no OpenSpec file outside the new change folder, and no Engram topic outside the new exploration topic are modified by this exploration.

## Business / Product Questions to Resolve Before Proposal

The orchestrator should ask the maintainer the following questions. Do not answer them for the maintainer.

- **Q1. First threshold table.** What numeric thresholds should the gate apply to the five `MetricSignal`s in the first archived slice, and which signals should be `block` vs. `escalate`? The current baseline is `outcome_classification 9/34`, `citation_exact_match 10/34`, `language_routing 34/34`, `sensitive_block 2/2`, `contradiction_detection 0/4`. A conservative first slice would set `sensitive_block = 1.0` (escalate), `language_routing = 1.0` (escalate), `contradiction_detection >= 0.0` (block, since the kernel still has work), `outcome_classification >= 0.0` (block, with a target ≥ 0.7 for a future slice), and `citation_exact_match >= 0.0` (block, with a future target). A tighter first slice would block the merge until the kernel reaches a higher bar. The maintainer must choose.
- **Q2. Per-scenario whole-answer rule set.** Should the gate evaluate the per-scenario rules on the existing 32 base scenarios + 2 injected cases (a 34-case rule set) or on a smaller, hand-picked subset that targets the cross-phase safety invariants (e.g. the 4 contradictory cases, the 2 sensitive cases, the 2 prompt-override cases, the 2 out-of-scope cases, the 2 provider-failure cases — about 12 cases)? The smaller subset is more reviewable and gives a clearer gate signal; the full set is more thorough but makes the first archived baseline harder to pass.
- **Q3. Gate report location.** Where should the gate report live (`evaluation-runs/gate/` as a sibling to `current/`, or a sibling `evaluation-gate-runs/`), how many runs are retained, and is the report treated as review evidence (committed) or local-only output? The previous quality-harness change committed `current/` and `previous/` under `evaluation-runs/`; the gate should follow the same discipline.
- **Q4. Escalation routing.** When the gate decides `escalate` (cross-phase safety invariant regression), what should the gate do? Options: (a) exit non-zero and write a reviewed escalation reason code, (b) exit non-zero and emit a separate "review needed" allowlisted record under `evaluation-runs/gate/`, (c) just exit non-zero with no extra record. Option (a) is the simplest and matches the existing harness discipline; option (b) gives the next change a clearer audit trail; option (c) is the no-change baseline. The maintainer must choose.
- **Q5. Strict TDD re-evaluation.** `openspec/config.yaml` currently has `strict_tdd: false` with the rationale "re-evaluate before application-runtime implementation." The gate is not application runtime, but the proposal should explicitly confirm or defer the re-evaluation, because the gate touches the release contract and the threshold table is a reviewed artifact. The maintainer should answer whether Strict TDD applies to the gate's threshold table, the runner, and the focused tests.
