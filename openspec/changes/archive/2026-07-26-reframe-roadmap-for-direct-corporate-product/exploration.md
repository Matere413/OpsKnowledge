## Exploration: reframe-roadmap-for-direct-corporate-product

### Current State

The OpsKnowledge roadmap (`RAG_ROADMAP.md`, 549 lines) is a single linear 0→10 path with four milestones (Validated foundations 0–2, Document-aware core 3–5, Pilot-ready product 6–9, Wider production 10). The product boundary states the corporate product uses approved, versioned technical collections, while a "development-only prototype" may use manifest-controlled synthetic technical entries that are visibly non-corporate and never migrate to a corporate index. The roadmap's current Phase 1 ("Minimal grounded OpsKnowledge core") was authored under that prototype framing: it positions itself as the smallest understandable pipeline that uses a synthetic corpus and an in-memory index, with approved-source sync, persistent storage, web UI, auth, analytics, conversation history, reranking, and framework-heavy orchestration explicitly deferred to later phases.

Phase 1 Work Unit 1 has already shipped: PR #28 `feat(minimal-grounded-core-pr1) → master`, merge commit `12ba6926`, 2,631 additions across 17 files, maintainer-approved `size:exception`. The change delivered the fail-closed corpus boundary (synthetic-only, profile-gated, CI denial), shared hexagonal ports (`Clock`, provider/repository protocols), and the corpus feature's domain/application/manifest-loader. The remaining Phase 1 work units (1.2 retrieval, 1.3 prompt builder, 1.4 generation provider, 1.5 outcome classifier, 1.6 CLI, 1.7 roadmap checkbox flip) per the active change's exploration are still on the planning surface — none has reached `master` yet. The `openspec/changes/build-minimal-grounded-opsknowledge-core/` directory still holds proposal/spec/design/tasks/exploration and is therefore not yet archived. The local `feat/minimal-grounded-core-pr1` branch is preserved; the remote head is deleted.

`AGENTS.md` separates two distinct prototype concerns that must not collapse into one another: (1) the development-only synthetic corpus exception (manifest-controlled, `development` profile only, CI denial) and (2) the accepted public-OpenAI free-text demo risk (synthetic documents/fragments only, high-confidence sensitive screen before any embedding/generation, rejected payloads do not persist, UI demo warnings, demo-only identities). Corporate users, corporate data, and the corporate MVP free-text path are explicitly forbidden from the public-OpenAI demo mode; corporate MVP free text uses Azure OpenAI or another approved controlled provider. `docs/architecture/platform-architecture.md` labels every runtime section as "prototype — target/planned" and "Prototype → Azure mapping and TI gates (target/planned)" and lists TI gates (Azure subscription/region/network, Entra group identifiers, budget ownership) as blocking; it does not claim any of the prototype stack is deployed.

There is precedent for a documentation-only roadmap rephrasing: `openspec/changes/audit-opsknowledge-phase-0-inputs/` is a still-open change that rewords Phase 0 pending inputs, the objective, and the Next step without implementing anything. `AGENTS.md` lists "Crossing the prototype/corporate boundary or changing the synthetic-corpus exception" among the changes that require a new SDD change.

A prior session summary (`opsknowledge` 2026-07-23 20:38) already established the prototype-to-product distinction: Phases 0–2 are validated foundations, 3–5 are the document-aware core, 6–9 are the pilot-ready product, 10 is scale-out. For a direct corporate path, the prior summary recommended merging Phase 1 into the production core, retaining Phase 2 as the safety gate, and front-loading Phase 8 identity/privacy/security gates instead of deferring them.

### Approaches

1. **Absorb Phase 1 into the production core, retain the PR #28 commit as the foundation, front-load Phase 8 gates** (recommended)
   Reframe Phase 1's objective from "smallest understandable pipeline that answers only from supplied textual evidence" to "production-core foundation: grounded retrieval, prompt construction, provider abstractions, outcome classification, and the per-request sensitive/demo gate, designed for the corporate MVP rather than a development-only synthetic prototype." Mark Phase 1's `[ ] Completed` checkbox as `[x] Completed` and reference the PR #28 commit + 2,631-line slice as the first delivered work. Add a one-line history note in the Phase 0/Pre-Phase-1 area explaining that the original "development-only synthetic prototype" framing was collapsed into the production core per this reframe, that the PR #28 corpus boundary is preserved, and that the development-only synthetic corpus exception is now a development-test fixture rather than a Phase 1 deliverable. Roll the remaining Phase 1.3–1.7 work units (retrieval, prompt, provider, outcome, CLI) into a renamed Phase 1.5/1.6 sub-section that targets the corporate provider abstraction and the per-request gate from day one. Move Phase 8 to be co-ordered with Phase 3–5 instead of after Phase 6–7, with an explicit note that identity, OIDC, sensitive screen, and TI gates are preconditions for the MVP rather than deployment polish. Keep Phase 2 (safety/quality evaluation) and the cross-phase safety invariants unchanged.
   - Pros: Preserves the PR #28 commit and the contributor's review as historical receipt; keeps the smallest understandable pipeline spirit; aligns Phase 8 with what the user wants (no identity/privacy/security deferred until the pilot); makes the development-only synthetic corpus exception a development-test fixture instead of a phase deliverable, which matches how the merged code actually behaves; bounded diff: only `RAG_ROADMAP.md` plus the small wording reconciliations in `AGENTS.md` and `docs/architecture/platform-architecture.md`; does not require any runtime change.
   - Cons: Requires explicit "rebranded from prototype" wording so future readers understand that the original Phase 1 framing was different; requires deciding whether the remaining Phase 1.3–1.7 work units belong in Phase 1 or roll forward into Phase 3/4/5; requires closing the `build-minimal-grounded-opsknowledge-core` change via archive (Work Unit 1 done) plus reopening the remaining work as a new bounded change; the "synthetic-only" emphasis of the merged code may look like scope drift if the reframe does not explain it.
   - Effort: Medium

2. **Keep Phase 1 as a discrete "minimal core" milestone and reframe it as the corporate MVP's first slice**
   Treat Phase 1 as a corporate MVP prerequisite: keep the seven-step plan from `openspec/changes/build-minimal-grounded-opsknowledge-core/exploration.md`, but reword the objective to "first production slice: grounded retrieval, prompt construction, replaceable provider, six-state outcome, per-request sensitive screen, and Azure-OpenAI-ready abstractions." Do NOT mark Phase 1 `[x] Completed` because the remaining work units (1.3–1.7) are not on master. Add a note that PR #28 is the first slice, not Phase 1 closure. Do not move Phase 8 ordering. Add a "Phase 1 → corporate provider" note that the provider abstraction must default to Azure OpenAI behind a feature flag and that the synthetic corpus remains the development test fixture.
   - Pros: Smallest possible diff to the roadmap; preserves the existing phase ordering without re-numbering; leaves the active `build-minimal-grounded-opsknowledge-core` change unmodified; reviewer-friendly because the change reads as a targeted reword.
   - Cons: Does not actually skip a phase, which is the user's stated goal; the development-only synthetic corpus framing still leaks into the narrative (the merged code references it as a hardcoded profile, not as a corporate target); the user has to read carefully to see that Phase 1 is now corporate-targeted rather than a "prototype"; Phase 8 stays deferred, which contradicts the user's intent of moving corporate security/TI gates earlier.
   - Effort: Low

3. **Eliminate Phase 1 entirely and renumber**
   Delete the Phase 1 section, promote Phase 2 to Phase 1, renumber 2→10 accordingly, and re-cite PR #28 as the Phase 1 deliverable under a new slug.
   - Pros: Aggressive simplification; aligns the roadmap exactly with "no prototype."
   - Cons: Violates the historical-receipt principle (PR #28 was authored and reviewed under the Phase 1 slug; deleting Phase 1 makes the contributor's review hard to locate); breaks every cross-reference (`AGENTS.md` Phase 0 completion note, `docs/architecture/platform-architecture.md` traceability table, Engram topics, the `build-minimal-grounded-opsknowledge-core` change folder, audit-opsknowledge-phase-0-inputs if it cites Phase 1); requires updating every doc that references phases by number; the change diff is large and may exceed the 400-line budget without chained PRs; breaks the instruction-hierarchy rule in `AGENTS.md` (the roadmap MUST NOT be renumbered without a new SDD change that explicitly handles the renumbering).
   - Effort: High

4. **Status quo with a roadmap addendum**
   Leave the existing phase boundaries and add a new "Direct-to-corporate path" addendum at the top of the document that explains the user can skip Phase 1.
   - Pros: Lowest possible diff; preserves all cross-references; safe for `AGENTS.md` instruction hierarchy.
   - Cons: Does not actually collapse the prototype framing, so the development-only synthetic corpus exception and the public-OpenAI demo risk remain the dominant narrative; leaves the roadmap in a contradictory state (addendum says "skip" but the body still requires Phase 1 as a forward phase); does not move Phase 8 earlier; the change reads as advisory rather than authoritative.
   - Effort: Low

### Risks

- **Phase 1 checkbox flip without archived evidence**: `AGENTS.md` explicitly forbids flipping a roadmap checkbox "from implementation status alone. Require the archived SDD report and its successful verification evidence." The reframe must close `build-minimal-grounded-opsknowledge-core` (Work Unit 1 verify-report + archive-report) before flipping the Phase 1 checkbox, OR keep the checkbox `[ ] Completed` and add a "history note" that the slice is merged but the change is not yet archived.
- **Collapsing the synthetic-corpus exception into the public-OpenAI demo risk**: `AGENTS.md` says "Do not merge them, do not generalize the synthetic-corpus exception into the accepted-risk mode, and do not describe the free-text path as 'synthetic queries.'" The reframe must keep these as two separate concerns even when the development prototype framing is removed.
- **Loss of historical receipt for PR #28**: deleting or renumbering Phase 1 makes the contributor's review hard to locate. The reframe must keep the PR #28 commit, the merge commit `12ba6926`, and the PR body discoverable from the roadmap text.
- **Phase 8 front-loading contradicts existing Phase 8 candidate SDD changes**: the existing Phase 8 candidate list (Entra SSO, Entra group authorization, versioned policy access gate, sensitive query preprocessing, controlled AI provider integration, security/access auditing) was scoped under a "post-pilot" mental model. Front-loading means those changes start before Phase 3 is done; the reframe must not assume the existing candidate list is the only work.
- **Instruction-hierarchy violation**: if `RAG_ROADMAP.md` contradicts `AGENTS.md` after the reframe, `AGENTS.md` wins. The orchestrator must run a final wording-check before submitting the change.
- **Scope drift into `build-minimal-grounded-opsknowledge-core`**: the reframe may be tempted to also reword the active change's proposal/spec/design/tasks. That is out of scope; the change archives as-is and the remaining work units reopen under a new slug.
- **Audit-opsknowledge-phase-0-inputs overlap**: that change is still open and may touch the same Phase 0 wording. The orchestrator should confirm with the user that this reframe owns the prototype-to-corporate transition, not the audit.
- **Cross-phase safety invariants must remain intact**: every "MUST" in the cross-phase safety invariant list is inherited from `RAG_ROADMAP.md` and is enforced by `AGENTS.md`. The reframe must not weaken any of them.
- **Engram topic state inconsistency**: the active change's Engram topics still describe the prototype framing. Closing the change in Engram and reopening the remaining work under a new slug avoids drift, but the reframe must do both in the same delivery.
