## Exploration: add-opsknowledge-quality-evaluation-harness

### Current State

The repository is at `master` with merge `e6234d17af283c2a2c3c232765fed13cc0cfede5` (PR #30). Phase 1 is **absorbed and reframed, not complete**: the deterministic grounded query kernel is the only production-core slice delivered. No runtime, FastAPI app, web client, database, embeddings, or live provider exists yet. The next step is the **first bounded slice of Phase 2 — Reproducible safety and quality evaluation**, scoped per the prior decision observation (Engram `#4727`) to a repeatable evaluation command, machine-readable report, execution of the reviewed synthetic dataset, and baseline metric output.

The merged kernel produces the six canonical outcomes (`supported`, `insufficient_information`, `contradictory_information`, `out_of_scope`, `unavailable`, `session_expired`) via a deterministic in-process application service:

- `backend/features/query/application.py` — `QueryApplication.resolve(...)` and the module-level `resolve_query(...)` helper, fail-closed on profile != `development`, no persistence, no provider network call.
- `backend/features/query/prompt.py` — immutable `GroundedPrompt` constructed from same-language approved fragments only; `GROUNDING_RULES` are the only rules payload.
- `backend/features/query/adapters/lexical_retriever.py` — `LexicalRetriever(Corpus)` over the dev synthetic snapshot, deterministic stdlib token-overlap ranking with stable ascending fragment-ID tie-break.
- `backend/features/query/adapters/fake_provider.py` — `FakeProvider` is a deterministic, in-memory `Generate` adapter that returns citation IDs for the supplied evidence, or maps `timeout` / `rate-limit` / `outage` aliases to typed `ProviderFailure`.
- `backend/shared/ports.py` — closed `SAFE_LOG_FIELDS`, six-state `OUTCOMES`, `GroundedPrompt`, `PromptEvidence`, `ProviderFailure`, `GeneratedAnswer`, `SafeResponse` (no answer/question/content fields, no persistence port).
- `backend/features/corpus/{domain.py,application.py}` — immutable `Entry` / `Fragment` / `EntryProvenance` with sha256 content hashes and fail-closed parent resolution.
- `tests/unit/test_grounded_query_kernel.py` — 331 lines of frozen contract tests for provenance, language isolation, lexical ranking, prompt boundary, screening, contradiction, citation allow-list, fake provider, and provider failure.
- `evaluation-dataset/` — 5 entries (8 fragments) and 32 deterministic scenarios (16 ES / 16 EN, 16 grounded / 16 abstention, 16 paired). The catalog carries only `case_type`, `expected_outcome`, `evidence[]`, `abstention_reason`, `safety_classification`, and `claim_expectation`. **No query text and no gold answer** are present on a scenario; this is intentional and protects the dataset from becoming accidental ground truth.
- `scripts/ci/validate_evaluation_dataset.py` — dependency-free structural validator wired into `make ci` before focused tests; enforces 32/16/16/16, paired fields, controlled vocabularies, hash integrity, language isolation, and prohibited scenario fields.
- `RAG_ROADMAP.md` Phase 2 (lines 169-205) names the metric set, the mandatory safety cases, and the acceptance direction ("no unsupported technical claim may pass the evaluation gate"); the three candidate SDD changes are `add-opsknowledge-quality-evaluation-harness` (this change), `add-technical-grounding-safety-gates`, and `add-language-and-abstention-evaluation`.

Authority order and invariants remain unchanged: `AGENTS.md` > `RAG_ROADMAP.md` > `docs/architecture/platform-architecture.md` > SDD artifacts. Excluded dependencies (LangChain, LlamaIndex, streaming, visual interpretation, email/Notifier, unevidenced reranking, Redis, queues, Kubernetes, microservices) and the prototype/corporate boundary (development synthetic exception vs. accepted public-OpenAI demo risk as two separate concerns) are preserved. `make ci` is the canonical local gate (`check-uv-version` → `sync-env` → `check-evaluation-dataset` → `check-focused-tests` → ruff/format/pyright/pytest → `check-dependency-boundaries` → `check-audit` → `license-inventory`).

### Affected Areas

- `backend/features/query/application.py`, `prompt.py`, `adapters/lexical_retriever.py`, `adapters/fake_provider.py` — **consumed unchanged** as the deterministic unit under evaluation. The harness invokes `resolve_query(...)` (or `QueryApplication.resolve(...)`) with a scenario-derived configuration. No kernel mutation.
- `evaluation-dataset/scenarios/*.json` — **consumed as the source of test inputs**. Scenarios already carry the data needed to drive a deterministic run: language, expected outcome, evidence identifiers, claim-expectation id, abstention reason, safety classification. Question text is **not** present and must be supplied by the harness in a controlled way (see open question Q1).
- `scripts/ci/validate_evaluation_dataset.py` — **unchanged**: dataset structural validation is already owned by the completed Phase 0 change. The harness must call it as part of its run and must not duplicate the rules.
- `tests/` — add focused unit tests for the harness under `tests/unit/test_quality_evaluation_harness.py`; add focused architecture/contract tests if the harness exposes a CLI. Follow the existing `tests/architecture/test_evaluation_dataset_ci_order.py` pattern that asserts validator order in `make ci`.
- `pyproject.toml`, `uv.lock`, `governance/direct-dependencies.yaml` — must remain unchanged: the harness uses only the stdlib and existing in-process modules. No new production dependency is required and none will be added.
- `Makefile` — extend with a `eval-quality` (or equivalent) target that runs the harness against the reviewed dataset; the target must keep `make ci` green and remain independent of the existing `check-evaluation-dataset` stage. Do **not** insert the harness into `make ci` until after the first archived run proves it is stable.
- `openspec/config.yaml` — the existing rules, the artifact store, the test command, and the workflow `execution_mode: interactive` already cover the harness. No config change is required by this exploration; downstream phases may add a focused `rules.evaluation` block.
- `openspec/specs/evaluation-dataset/spec.md` and `openspec/specs/grounded-query-kernel/spec.md` (the latter is in the merged-kernel change folder and must be archived/merged before a delta can be added) — the harness will **MODIFIED** the `evaluation-dataset` capability to add a runtime evaluator that consumes scenarios, and **MODIFIED** the `grounded-query-kernel` capability to assert that the kernel exposes the deterministic `resolve_query(...)` boundary the harness needs. Both edits require the source specs to be present in `openspec/specs/`, which is gated by the outstanding `build-production-core-query-path` archive pending the upstream Gentle AI authority repair (issue #1892). See Risks.
- `RAG_ROADMAP.md` — **no edit in this exploration**. The Phase 2 candidate checkbox for `add-opsknowledge-quality-evaluation-harness` may move from `[ ]` to `[x]` only on archived verification, not on this exploration or on proposal acceptance.

### Approaches

1. **Bounded in-process harness with a one-shot subprocess command and a JSON+JSONL report** — Implement a thin `backend/features/evaluation/` feature (domain + application + a single inbound CLI) that loads the dataset scenario catalog, derives a deterministic question fixture per scenario (paired with the matching corpus fragment content for grounded cases, a fixed language-coherent template for abstention cases), invokes `resolve_query(...)` against the in-process `LexicalRetriever` and a configurable `Generate` (the existing `FakeProvider` plus a `RecordingFakeProvider` that captures prompt evidence for citation-allow-list and contradiction checks), and writes one machine-readable report per run (JSON summary + JSONL per-scenario rows). The report records, per scenario: scenario id, language, expected outcome, observed outcome, observed reason code, observed citation set vs. expected evidence set, latency in ms (via a `Clock` injection, not `time.time()`), profile, and a pass/fail classification. The command is wired into a new `make eval-quality` target that does not enter `make ci`. No persistence, no HTTP, no live provider, no embeddings, no new dependency.
   - Pros: stays inside the development profile and the existing fail-closed boundary; consumes the kernel unchanged; uses the dataset's paired design to drive ES/EN parity checks; produces a machine-readable report usable by future threshold changes; respects the 400-line review budget for the harness by separating the report writer, the runner, and the inbound CLI.
   - Cons: question text is not in the scenarios, so the harness must derive it; the report schema is new and must remain forward-compatible with the later threshold and language-routing changes; running the harness adds wall time to the developer loop unless it stays opt-in.
   - Effort: Medium.

2. **Dataset-only structural re-run with a richer JSON report (no kernel invocation)** — Reuse `validate_evaluation_dataset.py` as the runtime evaluator and add a richer report that, for each scenario, cross-checks the expected evidence identifiers against the loaded `Corpus`. Do not invoke the kernel; assert schema and referential integrity only.
   - Pros: smallest change; reuses an existing dependency-free validator; no question-text problem; near-zero review risk.
   - Cons: does not exercise the kernel and therefore does not measure the Phase 2 metrics (Recall@K, answer correctness, citation validity, abstention rate, contradiction detection, language-routing accuracy, unsupported-claim escape rate). This is the same gap the prior decision observation explicitly listed as the next-step target. Rejected.

3. **Full Phase 2 evaluator with embeddings, live provider, metrics, and release thresholds** — Build the entire Phase 2 metric set, wire a live OpenAI provider, persist run history to PostgreSQL, and emit release-blocking thresholds.
   - Pros: strongest quality gates before further slices.
   - Cons: introduces a live provider, persistence, embeddings, and a dependency surface; collides with the prototype/corporate boundary; the merged kernel is explicitly Phase 1 foundational; threshold ownership belongs to a later `add-technical-grounding-safety-gates` change. Rejected for this slice.

### Recommendation

Use **Approach 1**. The change should enter proposal with the narrow scope of **a deterministic, in-process, dependency-free, development-profile-only quality evaluation harness** that:

1. Loads the 32 scenarios from `evaluation-dataset/scenarios/`, the manifest, the entries, and the fragments via the existing `load_corpus` boundary. Asserts dataset structural validity by invoking `validate_evaluation_dataset.validate(...)` first and aborts closed on any finding.
2. Derives a deterministic question fixture per scenario using a small, auditable mapping table. The mapping is paired ES/EN and must be reviewed; it is the only author-controlled question text and is **not** persisted in the dataset.
3. Configures `QueryApplication` with `LexicalRetriever(load_corpus(...))` and a `RecordingFakeProvider` that returns a configurable response per `case_type` and `expected_outcome` (or raises a typed failure for `provider-unavailable` cases), so the harness exercises the full six-state taxonomy without a network call.
4. Classifies each scenario outcome as **PASS** (observed `outcome` and `reason_code` equal expected) and additionally records:
   - Citation-set match: observed citation IDs equal expected evidence IDs for `supported`; empty for all abstention outcomes.
   - Language routing: observed routing equals scenario `language`.
   - Contradiction detection: observed `contradictory_information` for `case_type == "contradictory"`.
   - Sensitive block: observed `unavailable` with `sensitive_blocked` for `case_type == "sensitive-identifier"`.
   - Provider failure: observed `unavailable` with the right typed reason for `case_type == "unanswerable"` whose `abstention_reason == "provider-unavailable"`.
   - Latency in milliseconds via a `Clock` injection (no `time.time()` in the harness).
5. Emits a **machine-readable report** (JSON summary + JSONL per-scenario rows) and a **human-readable summary** (per-`case_type` and per-language counts of pass/fail, plus the full scenario catalog split). Files are written under a deterministic run-id directory; the runner is idempotent and accepts a `--report-dir` override.
6. Wires a new `make eval-quality` target that runs the harness against the reviewed dataset. The target is opt-in and does not modify `make ci`. The CI gate is **unchanged** for this change.
7. Stays inside the development profile; never logs content; never persists question, answer, citation, or provider payload; reuses the existing `emit_safe_log` / `SAFE_LOG_FIELDS` discipline and the `Clock` protocol; introduces **no** new production dependency, **no** live provider, **no** HTTP, **no** PostgreSQL, **no** embeddings, and **no** reranking.

The proposal should explicitly **exclude** live OpenAI/Azure adapters, embeddings, vector stores, persistence, HTTP, sessions, authentication, web UI, and release-blocking thresholds. The threshold change belongs to `add-technical-grounding-safety-gates`; the language-routing and abstention accuracy metrics belong to `add-language-and-abstention-evaluation`; embeddings and live providers remain Phase 3+ / Phase 8.

The orchestrator should expect an authored-line forecast near the 400-line budget, with the runner, the report writer, the CLI, the question-fixture table, and the focused tests each contributing. The forecast should be split by work unit in the tasks phase so the ask-on-risk decision can be made before any code lands.

### Risks

- **Outstanding kernel archive blocks the delta spec.** `openspec/changes/build-production-core-query-path/specs/grounded-query-kernel/spec.md` is still inside the active change folder. A delta against the `grounded-query-kernel` capability cannot be merged into `openspec/specs/grounded-query-kernel/spec.md` until that change is archived. The proposal should plan to either (a) add the harness requirements under a new `quality-evaluation-harness` capability that does not require modifying the kernel spec, or (b) accept a sequencing dependency on the kernel archive and resolve only after upstream Gentle AI issue #1892 is repaired. This is a sequencing risk the maintainer must resolve.
- **Question text is not in the scenarios.** The dataset explicitly forbids `query`/`question`/`text` fields. The harness must derive a question per scenario from a reviewed fixture table. Without that table, the harness cannot run end-to-end against the dataset, and a fabricated table would weaken the safety story. Treat the question-fixture table as a reviewed artifact belonging to the change.
- **400-line review budget is the binding constraint.** The merged kernel already exceeded 400 lines under a maintainer-authorized size exception. The harness plus tests plus the question-fixture table plus the Makefile wiring is likely to land in the same band. The tasks phase must forecast the budget per work unit and ask before splitting into chained PRs.
- **Prototype/corporate boundary must not blur.** The harness runs only under the development profile and the existing fail-closed synthetic boundary. A future change that wires the harness into a live OpenAI/Azure provider, or that reuses it against corporate data, would violate the boundary and require a separate SDD change.
- **Excluded dependencies and reranking.** The MVP adds FTS + RRF only if evaluation proves value (architecture, "Excluded dependencies and surfaces"). The harness must not introduce any reranking, embeddings, or vector-store dependency; it must use the merged kernel's lexical retriever unchanged.
- **No content in logs or reports.** Latency, outcome, reason code, language, profile, provider class, and run id are safe. Question text, answer text, citation content, scenario `claim_expectation` text, and provider payload text are not. The report schema must be reviewed against `SAFE_LOG_FIELDS` and the `SafeResponse` content-free surface before merge.
- **Clock and determinism.** The harness must inject a `Clock` and a frozen `FrozenClock` in tests; using `time.monotonic()` directly would break determinism and the `make ci` reproducibility contract.
- **Makefile ordering.** Adding a new `make eval-quality` target must not perturb the existing `make ci` order. The new target is opt-in; `check-evaluation-dataset` continues to run first inside `ci` and now becomes a true prerequisite that the harness also calls.
- **Roadmap completion discipline.** The Phase 2 candidate checkbox for `add-opsknowledge-quality-evaluation-harness` remains unchecked until archived; this exploration and the proposal do not complete the phase. The maintainer must not be told otherwise.

### Ready for Proposal

**Conditional Yes.** The repository evidence is sufficient for a proposal **provided the orchestrator confirms three sequencing decisions before the proposal phase runs**:

1. The proposal will create a new `quality-evaluation-harness` capability and will **not** add a `MODIFIED` requirement against `grounded-query-kernel` until the kernel change is archived. This avoids a hard sequencing dependency on upstream Gentle AI issue #1892.
2. The question-fixture mapping table is a reviewed artifact of this change, not of the dataset; the dataset validator's prohibited-field list is unchanged.
3. The first slice emits a **baseline** report (numbers, not thresholds); release-blocking thresholds stay in `add-technical-grounding-safety-gates`.

No code, no existing artifact, no OpenSpec file outside the new change folder, and no Engram topic outside the new exploration topic are modified by this exploration.

### Business / Product Questions to Resolve Before Proposal

The orchestrator should ask the maintainer the following five questions. Do not answer them for the maintainer.

- **Q1. Question text for the reviewed dataset.** The dataset deliberately carries no `query` / `question` / `text` field on a scenario. How should the harness obtain a deterministic, auditable question per scenario: (a) a reviewed in-repo mapping table per scenario pair, (b) a generator template derived from the expected evidence content with a deterministic seed, or (c) a curated reviewer-authored `evaluation-dataset/questions/*.json` companion that is structurally validated by the existing validator? Each option has a different review footprint and a different risk of becoming accidental ground truth.
- **Q2. Scope of the first baseline.** The roadmap lists nine Phase 2 metrics and seven mandatory safety cases. Should the first archived run report **all nine metrics** for the 32 scenarios, or a smaller initial subset (e.g., outcome classification, citation-set match, language routing, sensitive block, contradiction detection) with the rest deferred to `add-language-and-abstention-evaluation`? The smaller subset keeps the review surface aligned with the merged kernel and avoids metrics whose measurement requires features not yet implemented (e.g., semantic contradiction labeling).
- **Q3. Question of provider-failure coverage.** The 32 scenarios cover the six outcomes but do not include a scenario with `abstention_reason == "provider-unavailable"`. Should the harness add a synthetic `provider-failure` scenario pair (one ES, one EN) under a clearly-labeled "harness-injected" tag so the first archived run proves the typed-failure path, or should provider-failure coverage wait for a dataset change in a later slice?
- **Q4. Report location and retention.** Where should the run report live (`evaluation-dataset/runs/<run-id>/` inside the dataset, a sibling `evaluation-runs/` directory, or a developer-local `var/runs/` ignored by git), how many runs are retained, and is the report treated as review evidence (committed) or local-only output? The choice affects whether the report becomes a governance artifact.
- **Q5. CI gate wiring.** Should the first archived harness be wired into `make ci` immediately, kept behind a separate `make eval-quality` opt-in target for one cycle, or wired in only after the next archived run proves stability? The current canonical gate is intentionally narrow; widening it is a separate decision and should be explicit.
